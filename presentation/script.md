# 発表原稿

就職作品プレゼンテーション用の発表原稿です。動画の場面(`video/compositions/` の各ファイル)と 1 対 1 で対応しています。
数字は 2026-11-07 にダッシュボードの公開 API から取った値です(1.0 の事例は Thunderstore の値)。日付は日本時間です。

目安の長さは約 4 分 30 秒です(1 分あたり約 280 字)。「〇〇」は発表者の名前です(名前はリポジトリに入れない)。

## 1. hook(1.0 の日)

2026 年 10 月 28 日、ゲーム「SULFUR」の正式版 1.0 が出ました。
この更新で、わたしが公開している mod のうち 6 個に修正が必要になりました。
今日は、直すまでに修正前の版が何回ダウンロードされたかを、数字で出せるシステムを紹介します。

## 2. title(作品名と自己紹介)

HAL 東京、情報処理学科の〇〇です。
作品名は「Mod Insight」です。

## 3. purpose(企画の目的)

わたしは Thunderstore と Nexus Mods という 2 つの配布サイトで、ゲームに機能を足す「mod」を 25 個ずつ公開しています。ダウンロードは合計で 5 万を超えました。
ただ、どちらのサイトも見られるのは今の合計だけで、昨日何件増えたのか、ゲームの更新で何が変わったのかは分かりません。
そこで、毎日 0 時に両方のサイトから数を取って保存し、推移をグラフで見られるようにしました。

## 4. audience(誰に見てほしいか)

見ていただきたいのは、IT 企業の方です。
データの取得からデータベース、クラウドへの配置、監視、費用の確認まで、ひとりで作って毎日動かしています。
API で数が取れるものなら、EC サイトの商品やアプリにも同じ作りで使えます。

## 5. architecture(システム構成)

構成です。毎日 0 時に Azure Functions のタイマーが動き、2 つの配布サイトと、Steam にあるゲームのお知らせを取りに行きます。
サイトごとに API の形が違うので、アダプターで共通の形に直してから Azure SQL Database に保存します。サイトを増やすときは、アダプターを 1 つ足すだけです。
無料枠のデータベースは使われないと止まるため、その日最初に開いた人は約 50 秒待たされていました。
データは 1 日 1 回しか変わらないので、取得のあとに API の応答を Blob Storage に作っておき、ふだんはデータベースを起こさないようにしました。
配置は GitHub Actions で、テストが通ったものだけを自動でデプロイします。

## 6. case(1.0 の 8 日間)

では、1.0 の話に戻ります。
グラフの縦線がゲームの更新です。1.0 のあと、30 日に 1.0.1、31 日に 1.0.2 と修正版が続きました。
大きな更新の直後は小さな修正が続くことが多いので、1.0.2 を待ってから直すことにしました。
6 個とも、11 月 1 日から 5 日までに新しい版を出しました。かかった日数の中央値は、1.0 から数えると 5.5 日、1.0.2 から数えると 2.5 日です。
そのあいだに、修正前の版は Thunderstore だけで 712 回ダウンロードされていました。多めに見積もった数ですが、待っているあいだも古い版を入れる人がこれだけいた、ということです。
次に大きな更新が来たら、すぐ直すか少し待つかを、この数字を見て決めます。

## 7. operations(運用)

運用では、取得の失敗や API のエラーが続いたら、メールで通知が届くようにしています。
監視のアラートは本数と時間で料金がかかり、最初の 3 本のままだと月 225 円ほどになる計算だったので、1 本にまとめました。10 月の費用は 95 円です。
本番で起きた問題は、原因と対応を記録に残しています。

## 8. next(今後)

今後は、データベースへの接続を、パスワードを使わない方式に切り替えます。
また、学生向けの Azure の利用枠が 2027 年 9 月に切れるので、それまでにデータを静的なファイルに書き出し、費用をかけずに公開を続けられるようにします。

## 9. close(まとめ)

Mod Insight は、自分の mod のデータを毎日集めて、更新の判断に使えるようにしたシステムです。
ご清聴ありがとうございました。
